2. The three blockers

2.1 Free-tier limit disagrees in four places

WhereLimitEffect
RLS insert policy on calculations (migration 20260126000002)3The database rejects the 4th save.
Landing pricing section3What users are told.
checkCalculationLimit() in lib/supabase/calculations.ts5Client lets the user try saves 4 and 5.
New Settings page usage meter5Shows "3 of 5 calculations" then the next save fails with an RLS error.

This is a product decision. Pick one number and change the other locations. If it stays at 3, the fix is two constants in the web app. If it becomes 5, it needs a migration that rewrites the RLS policy on both DEV and PROD.

2.2 Settings name save has never run against real RLS

The Settings page does a client-side UPDATE users. Nothing in the app has done that before. The save API route uses the service role for its user upsert, so the "Users can update own profile" policy has never been exercised. Its WITH CHECK clause runs a sub-select on the same users table, a pattern that sometimes trips Postgres policy recursion. It probably works because the SELECT policy is a plain auth.uid() = id, but "probably" is not verified. Log in on the DEV project, change the display name once, and confirm it persists before calling Settings done.

2.3 /compare is not a protected route

The middleware guards /dashboard, /calculations and /settings server-side. Compare redirects client-side after the page renders, so an anonymous visitor sees a spinner and a flash before bouncing to login. One-line fix in apps/web/lib/supabase/middleware.ts:

const protectedRoutes = ['/dashboard', '/calculations', '/settings', '/compare']

5. Improvement roadmap

Ordered by impact relative to effort. The first group are correctness issues in code that already exists.

5.1 Fix now (small, real bugs)

  • Property-management dollar mode is still ignored in the shared projections package and in the Compare "Mgmt Fee" row. The Jan 30 session notes already flagged the package side. Since Compare now draws a 30-year chart from those projections, the chart is wrong for any dollar-mode property. Fix in packages/calculations/src/projections.ts and add a test.
  • "Upgrade to Pro" in Settings does nothing. Either link it to /signup?plan=pro like the pricing page or hide it until billing exists.
  • Lint is unusable repo-wide. Add "@repo/eslint-config": "workspace:*" to the web app's devDependencies. Expect a backlog of warnings once it runs, so budget a cleanup pass.
  • Declared Pro features the app does not gate. Pricing promises "30-year projections", "side-by-side comparison" and "PDF reports" as Pro-only, but Compare and PDF are available to everyone. Decide whether to gate them or reword the pricing copy.

5.2 Harden the listing import endpoint

POST /api/properties/extract is unauthenticated, has no rate limit, and its curl fallback uses execFileSync with a 20-second timeout. On Vercel's Fluid Compute one slow scrape blocks the event loop for every other request sharing that instance. Also, curl's presence in the runtime image is not guaranteed, so the fallback may silently be a no-op in production.

5.3 Product and growth

  • Billing. The pricing page advertises $9.99/mo Pro but there is no checkout. The schema already has RevenueCat columns and the roadmap lists Stripe. This is the single biggest gap between what the site promises and what it does.
  • Rent estimate on import. After a Zillow/Redfin import the user still has to type rent. A Zestimate/Rentometer lookup, or even a simple 0.8 to 1 percent rule-of-thumb default, would make the import feel complete.
  • Shared view as a lead magnet. The public /s/[token] page is a natural acquisition surface. Add Open Graph images and a stronger "analyze your own deal" call to action.
  • Investment Metrics education card on the dashboard still says "Coming soon". Either write it or remove it.
  • OAuth providers (Google, Apple) are listed as pending in TO-DOS.md. Login friction on a calculator app is a real conversion cost.

5.4 Engineering hygiene

  • step5-results.tsx is 1,246 lines and duplicates metric computation that ComparisonView now reimplements again. Extract a single computeResults(formData) helper into the calculations package so the wizard, compare, save route and shared view all agree.
  • No CI for build/test. Only the Claude review workflow runs on PRs. Add a workflow that runs pnpm type-check, pnpm test and pnpm build.
  • Integration and E2E tests remain unstarted per TO-DOS.md. The compare flow and the save/limit path are the two highest-value targets.
  • DEV/PROD schema drift check is still manual. The tier-limit mismatch above is exactly the kind of thing an automated diff would catch.
  • Docs are stale. NEXT-SESSION.md still describes the Phase 2 branch from January. Update or delete.

6. Suggested path to publish

Two options. Both keep this branch, since main is only one trivial workflow commit ahead.

  1. Decide the free-tier number and align the four locations (section 2.1).
  2. Add /compare to protected routes (section 2.3).
  3. Verify one Settings name save on DEV (section 2.2).
  4. Remove stray files, then commit in two pieces so the history stays readable:
rm -f *.png .sync-conflict-*.DS_Store
git add apps/web/app/\(dashboard\)/compare apps/web/components/comparison \
        apps/web/app/\(dashboard\)/calculations/page.tsx \
        apps/web/components/dashboard/sidebar.tsx apps/web/app/globals.css
git commit -m "feat: Side-by-side property comparison with PDF export"

git add apps/web/app/\(dashboard\)/settings apps/web/lib/supabase/user-settings.ts \
        apps/web/lib/supabase/middleware.ts
git commit -m "feat: Settings page with profile editing and plan usage"

git push
gh pr create --base main --title "feat: Compare, Settings, PDF export, address hint"

Merging to main deploys production automatically through the Vercel git integration, so treat the PR merge as the release step. Option B is to move Compare and Settings to their own branch and merge the address hint alone first. That is cleaner history but delays the Settings 404 fix.
